# 普通队伍领域接线合同（2026-10-18）

本合同只覆盖公开领域源码，不包含完整宿主或原生封包实现。领域测试通过不等于游戏可玩。

## 容量与身份

普通队伍容量最多四人，SharedRun 支持固定的 2–4 人成员快照。单人继续使用宿主原有路径。频道在线人数、普通队伍人数与团本分队容量是不同概念；这里没有整服四人限制，也没有扩大原生槽宽。

每个 ordinary.Service 必须由可信宿主按认证范围独立创建。party.Lease 是已选择角色的领域代次，不是登录凭据。Bind 不认证账号；不能把客户端上报的 actor、角色或范围直接当成可信身份。

AcceptFrom 只验证领域内邀请 ID、方向和双方精确代次。宿主仍须同时保护邀请双方的账号租约与完整选角状态；它不证明原生客户端的接受按钮语义。历史 Accept 保留作领域兼容入口，不应直接暴露给原生请求。

## 加载、提交和释放

1. 成员由真实 Hub 形成队伍，Start 固定成员、角色代次和稀疏槽位。
2. 每名成员自己的地图批次真正写出后才调用 MapsWritten。
3. Loaded 只接受同一 run/room 和精确成员代次；全员到齐后进入 SharedReady。
4. 宿主持稳定排序的全部账号租约，再持全部完整选角守卫，通过 Service.WithRoomCommit 覆盖原 Store 的有界 SQL 事务与 commit。
5. 只有事务成功才由可信宿主调用 Release，进入 SharedRunning；事务未知或失败时不调用 Release。Release 自身不读取数据库、不验证收据，不能作为客户端可调用接口。

锁顺序为：全部账号租约 → 全部选角守卫 → Service → SharedRun → 原 Store。事务回调不得回入 Service/Hub/SharedRun、发送网络或触发观察者。锁等待不受 context 中断，数据库回调应由宿主单独设置时限。

超时、退队、断线、换角色或队长变化必须在宿主角色生命周期中同步失效，不能仅依赖异步通知。原 run 取消后不能悄悄减少固定入场人数，剩余成员须另建新 run。队长继任保留成员原槽位。

## 战斗与资产边界

Kill 只确认已释放共享房间中的实体死亡，重复报告不产生第二次变化。ClaimDrop 仅预留内存中的领取归属，不是物品入库或结算凭证；真正资产写入仍归宿主唯一 Store。

源码没有实现资源退款、Confirm/Cancel/recovery 完整协议。提交成功后若释放失败，不能据此猜测自动退款；宿主必须依据持久记录和明确恢复策略处理。

当前不提供原生邀请/名册/进图/战斗成功封包，不宣称四客户端实机、跨机器连接或在线压力验收。partywire 仍是 B823 已证逻辑体的离线解码器；未知字段不填零作为发送供值。
